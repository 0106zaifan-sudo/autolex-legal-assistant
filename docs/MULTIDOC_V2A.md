# V2.0-A 多文档证据关联

基线ac528ad6，分支feature/v2-multidoc-evidence。原工作区干净，独立worktree开发。本轮不调用模型，不读取Secrets或真实案件/私有验收记录，不部署。

## 操作

1. 上传多份PDF/DOCX，创建案件并明确将所选文档加入同一案件。
2. 在本案原文文件中选择位置，保存连续引用。自动候选只比较已经保存的证据，不把全部文件正文或同名文件自动合并。
3. 点击“发现本案证据关系候选（离线）”。选择候选后，两列显示独立原文、文档ID、原文件及解析快照SHA256、位置及字符范围。
4. 选择关系审阅状态及类型，填写复核人和理由，追加审阅。原候选保持candidate，所有历次审阅及前一审阅ID保留；最新审阅单独显示。
5. 下载案件JSON。它包含关系、审阅、证据索引及原事实/主张/时间线/待核实事项，不内嵌原始字节。导出前重新验证锚点。原文件仍由原有独立下载入口保留。

四份完全虚构样本位于samples_multidoc：现场记录PDF、驾驶人陈述DOCX、企业说明DOCX、电子数据摘要PDF。文件名及正文均注明模拟。可全部上传归入同案；选择事件编号所在的具体原文句，保存证据，比较现场08:30与摘要08:31，以及企业发出与驾驶人收到的不同命题。电子摘要的“原始日志未提供”仅描述本材料范围，不能推断日志现实中不存在。生成脚本make_multidoc_samples.py不涉及原SIM_A/B，也不生成模型结果。

## 技术及边界

复用原CaseStore多文档归档和evidence.make_span/verify_span，不修改原证据算法。关系引用双方独立evidence_id，经本案证据表绑定文件SHA256、解析快照、document_id、unit和坐标。跨案件、同文档和改名的相同原始字节副本拒绝关联。相同文本但不同来源保留不同锚点。

有限规则在evidence_relations.py：

- 无共同主题或明确不同事件编号，不自动关联。
- 缺共同事件编号，只标needs_verification；编号仅是材料字面标签，不证明同一真实事件。
- 相同编号、同一明确字面命题（系统发出/驾驶人收到分别比较）同向为support_candidate，反向为inconsistency_candidate。
- 发出与收到不同，标related，不能直接判矛盾。
- 正向碰撞记录的唯一可解析日期/时间，同精度同值/异值仅为支持/差异候选；精度不同或时间歧义、缺失则needs_verification。时区、时钟校准及来源真实性没有确认。
- 仅主题相同只能related；遇未提供、待核实或含糊表达保留待核实。不得依据单个否定词判断法律矛盾。

自动发现最多比较150个已保存锚点；先全部校验再生成。重复/反向点击不重复建关系，不覆盖旧候选或旧人工审阅。关系人工确认不会触发confirm_fact或生成事实认定，也不认定责任。原安全门禁、模型限额和单文档AI均未改。

规则是局部字面识别，不是语义推理：未覆盖措辞、复杂否定、引语、多事件宽引文可能漏报或误报；请选窄且完整的句段。不同文件仍可能互相抄录，候选支持不是独立互证。来源不明和时钟差异必须人工核查；本阶段不会自动对齐时间或裁决矛盾。未保存为证据的内容不参与比较。

## Schema兼容

新案件schema_version=1.1，新增relations与relation_reviews，其他结构保留。CaseBundle仍接受标记1.0的内存结构，缺新字段默认空，不产生确认结果。旧导出JSON可由case_schema.upgrade_case_payload显式转换：只接受1.0且无非空关系/审阅，深拷贝保留原字段并加空列表。不修改原输入，不把旧数据升级为已确认关系。

这不是恢复导入API。既有案件JSON不含原始字节，不能仅凭JSON恢复可验证证据；本轮仍需会话中明确归档的原件。原review列表专用于事实真实性复核，新的relation_reviews只记录关系审阅，两者不混用。
