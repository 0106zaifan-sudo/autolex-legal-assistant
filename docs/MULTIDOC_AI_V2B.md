# V2.0-B：案件级AI联合分析

基线：`feature/v2-multidoc-evidence` 的 `360911ff7a`。独立分支：`feature/v2-multidoc-ai`。开始时原工作区干净，使用独立worktree，未覆盖用户修改。没有读取真实案件、实际Secrets或私有验收文件，没有运行真实API、部署或合并。

## 操作闭环

1. 按V2.0-A流程创建案件，明确归档PDF/DOCX。
2. 在“AI 多文档综合分析”中选择本案2—4份材料。页面逐一列出文件名、文档ID及SHA256。
3. 每份解析覆盖不完整的文件分别查看风险并确认；失败/无文字/版本错误的文件即使确认也不能发送。
4. 本批次另行勾选发送授权。它不复用单文档同意状态；案件、文档快照、解析风险、服务商、模型或登录主体改变会重置。每次点击后无论成功失败都消耗本次同意，下次必须重新勾选。
5. 点击“一次请求”按钮才发起SDK调用。不逐文件调用，不自动重试。身份/密钥/公开单实例要求、原SQLite额度、并发租约、冷却、输入累计预算和默认45秒进程截止继续生效。
6. 分析先在会话中预览，包含事实/主张、各文档事件、关系、待核实问题及有限诊断。需要保留时下载联合分析JSON。
7. 再点击“明确导入本案”。当前档案和结果重新校验，全部成功后一次替换本案副本；失败不写入部分证据或候选。
8. 在原关系复核区并排查看原文。AI候选保留原建议、模型/批次标识及备选摘录；人工确认、修改、驳回沿用原追加审阅链。切换关系后清空上一候选的审阅表单，避免误复用。

切换批次会清除临时预览和旧回执；退出登录/清空本会话也清除联合数据。回执只在对应案件和批次展示。没有新的密钥输入框，也不需要新增Secrets配置。

## 独立协议与来源

模型Schema：`multidoc-analysis/1.0`；Prompt：`multidoc/v1`。沿用官方OpenAI Python SDK和Responses API、固定官方端点以及现有DeepSeek参数适配。未更改单文档Schema 2.0或单文档AI代码。

原始输出只含case_id、batch_sha256、版本和四类列表：facts、timeline、pending_evidence、relations。事实kind只接受事实/主张；问题kind只接受推断。所有引用为source_id+连续quote。关系含左右独立引用、候选类型及带“待核实推断：”和问号的问题表达，不含可信坐标或模型自报文件哈希。

后端来源清单每项含case_id、document_id、原件SHA256、解析快照SHA256、解析器版本、全局MD_编号、unit、位置、字符起止和原文。MD_编号由案件、文档和原文范围派生，批次内唯一性在调用前检查。相同文字不同文档保留独立来源；本批次不接受S001等局部编号。

batch_sha256绑定案件、所选文档/解析报告/来源、服务商、模型、协议版本及Prompt哈希。模型必须逐字回传，跨案件、过期批次或被替换材料拒绝。模型输入不包含单文档局部编号映射。

校验时从当前CaseStore原件和快照重新执行make_span，不能只信清单或模型返回的文件名/位置/哈希。事实和事件的引用限单个文档，避免拼接双方陈述成客观事实；跨文件论点通过关系和多引用待核实问题表达。每个引用都必须有效，不能用一条正确引用掩盖另一条错误引用。

内部将全局编号映射到对应文档的单文档校验协议，复用原严格分类、引文、时间绑定和P1质量检查，引用文字不变。`per_document`是按明确document_id分隔的后端2.0投影，供原CaseStore重验，不用于跨文件定位。外层facts/timeline以及模型引用与source_manifest使用全局ID。映射不是对失败引用的自动纠错；未知ID或错误quote不会搜索其他文件替代。

## 时间和关系判定边界

事件逐文档保留，原文分别记载08:30和08:31就保留两条，不选最终时间，也不按不同文件时钟推断因果。无日期事件按原unknown/unknown/未知/null绑定。新的跨文件碰撞时间/精度差异提示只标needs_review，提醒事件同一性和时钟未确认，不制造关系或事件。

AI的support_candidate/inconsistency_candidate还需满足V2.0-A有限的同事件/同命题或同精度时间对照规则。发出、送达、收到/感知是不同命题；若规则只支持related/needs_verification，AI强关系整批拒绝，不静默降级。这个限制可能拒绝原文有语义支持但现有字面规则未覆盖的强建议，应先用一般关联/待核实候选并人工复核。

related/needs_verification仍要求左右独立原件、完整锚点和合法推断表达，但不宣称语义已证明。改名的同字节副本不能作为两个独立关系端点。

所有关系的status固定candidate，semantic_status始终pending_human_review。格式通过、引用/时间绑定通过和语义人工审查分开记录。强关系被保守策略拒绝时，回执保留evidence_status=passed及semantic_status=rejected_by_conservative_policy，不能声称整个分析通过。

待核实问题必须有至少一个有效引用，正文是某条引用的原文，reasoning只提问。沿用原法律引用、病句等保护，并拒绝引用中没有支持的日期、未涉及的EDR/DSSAD，以及日志必然存在/已经缺失等明确断言形式。规则不是完整语义证明，模型角色分类、隐含新假设及责任措辞仍须人工核查，不能自动认定真实性或责任。

每份文档沿用有限的时间线完整性诊断，并纳入该文档相关的联合待核实问题；事件如果在facts和timeline都漏掉，或措辞未覆盖，不能保证发现。不自动补事件或问题。

## 导入、去重与案件Schema

先重建整批canonical结果并逐项比较，拒绝篡改后的引用、坐标或过期结果。再在案件深拷贝中复用CaseStore.import_analysis、add_evidence、Statement和PendingItem，最后一次提交。本案之外的案件不改动，旧事实/主张、人工真实性复核、时间线和关系审阅保留。

AI关系method=ai_multidoc/v1，不调用confirm_fact。相同类型/相同问题且双方属于同一文档位置、连续摘录有包含及位置重叠时，可复用一个AI候选；所有原建议及备选左右锚点仍存ai_origins。不合并不同文件来源或不同问题，也不覆盖旧离线候选及人工审阅。措辞不同的近义问题不会自动去重，可能仍显重复。

导入联合分析后案件显式升级为1.2，新增非空ai_origins及analysis_receipts。旧1.0/1.1仍可读；新建普通V2.0-A案件继续默认1.1。新字段为空时不导出，因此旧1.1导出不会混入空新字段。后续离线关系操作不能将1.2降级。此升级发生在用户明确导入操作，不产生已确认事实或已确认关系。原1.0显式转换工具不改变。

案件导出继续排除original_bytes，并验证原证据。安全回执按白名单保存，保留模型、usage、Prompt哈希、文档快照、预算与验证状态，排除任意Authorization等字段。重复导入相同run_id不重复写回执。模型元数据和手填审阅人不是身份认证或SDK真实性的数字签名，引用校验仍以原件为准。

## 安全与规模

联合输入单文档最多8000字符，整批最多16000字符、96来源块，2—4不同document_id。超限、来源编号冲突、文档ID/原件/快照不符或解析失败在模型调用前阻止。不静默截断或发送部分材料。

完整请求UTF8字节（含Schema、Prompt、报告和余量）仍受原max_request_bytes及累计额度约束；字符预留不是实际token数。一个实际SDK请求只原子预留一次额度，失败也计次和占预算，不重置旧账本。联合输出上限6000 token，SDK零重试及原总截止不变，超时不能证明远端未计费。

使用现有服务商凭据读取和访问控制，不增加环境回退或配置入口。普通日志不打印原文、模型响应、密码或API Key；失败提示为固定安全文本，回执保留安全错误代码。结果、来源与AI审计包含原文，属于私有案件数据，只在授权会话及明确导出中使用，不进入Git或源码ZIP。原有私有模拟失败捕获不扩展到联合分析。

## 离线验证

先新增19项规格测试，旧基线因缺少联合入口失败；随后实现并逐步增加源冲突、时间、语义边界、SDK mock、UI及原子导入等测试。时间测试改为对独立单句引用绑定其实际原文时间，而不是把材料事件编号和分号后的事件混成一句，未放宽原时间校验。精度测试第二次请求使用推进的模拟时钟，仍保留失败的第一笔配额，不重置账本。

最终测试结果见TEST_REPORT及multidoc_ai_offline_tests.txt。所有新AI测试只用本地HTTP MockTransport或内存注入；包含OpenAI/DeepSeek官方SDK序列化通路测试，不能当真实模型效果验证。UI隔离helper保留原模型禁调用断言，并新增联合入口禁调用断言；原测试意图不变。

## 剩余限制与下一次最小真实方案

本轮不证明DeepSeek实际生成完整/准确。格式与锚点通过不等于问题合理或关系成立；简单字面规则可能误拒强关系，未覆盖表达可能漏检。不合并所有近义建议；时间展示不是跨时钟的统一排序；PDF无OCR，遗漏区域只能风险提示。案件JSON恢复导入及多租户权限、数字签名不在本轮。

人工先审查代码、完整离线日志和UI流程，再决定是否单独授权付费验收。最小建议：一次选择模拟驾驶人陈述+企业说明，检查一次请求、主体主张及发出/收到区分、独立全局来源、额度和拒绝路径；再另行授权一次四份既有模拟材料，逐份确认PDF覆盖风险，核对08:30/08:31两条记录、时间差异提示、待核实问题、显式导入与审阅历史。未知时间可用既有模拟材料另设受控批次验证，不能从离线通过推定已通过真实验收。

两阶段均不得自动重试。保存私有回执和人工判断，不提交真实模型响应或Secrets。本轮在代码交付后停止，未运行任何真实付费验收、部署或合并。
