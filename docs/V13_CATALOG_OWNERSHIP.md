# AutoLEX 1.3：证据目录哈希由程序管理

基线feature/v2e-schema-diagnostics / 0e65f9501c65d9384b812c56b75aac0b98b44613；独立worktree与feature/v2e-program-owned-catalog-hash分支，开始前基线干净。

## 已确认问题与最小方案

用户提供的第五次真实安全回执显示：completed、format失败、唯一Schema错误为missing / [pending_catalog_sha256]，evidence=not_run。这足以确认旧1.2响应缺少该必填字段；其他字段未报告Schema错误不代表编号、引用、事实或语义已核验。本轮没有读取该真实响应或私有运行资料，也不修改、补齐或导入它。

目录SHA是程序从可信文件、解析快照及证据坐标计算的确定性状态，要求模型回传它增加复制依赖，并不提供额外的真实性证明。采用明确multidoc-analysis/1.3、multidoc/pending-selection-v2，将它完全从响应Schema中删除；不是改成可选或给缺失值设默认，也不是收到旧响应后补字段。

模型仍须原样返回case_id、batch_sha256及版本，仍明确选择pending_evidence的anchor_id、全部evidence_ids和reasoning。待核实事项仍不允许自由text、quote、坐标、kind或哈希；facts、timeline、relations的契约及同次请求分析保留。根对象additionalProperties=false：1.3额外返回pending_catalog_sha256也会拒绝，不能静默忽略旧字段。

## 程序拥有目录状态的完整链

1. 请求前按1.3 Schema/Prompt生成独立批次指纹，复用pending_catalog.py从当前档案验证原件SHA、解析SHA、解析器版本、文档ID、原文坐标及完整行。目录版本与哈希由程序计算并保存在本次批次和调用回执。
2. 请求发送原文来源和紧凑PE编号映射，不发送顶层目录哈希回传字段，目录紧凑映射也不再给出要求回传的目录SHA。原文文件哈希等仍按原来源清单保留。模型只负责语义选择，不负责证明目录完整性。
3. SDK返回后先严格解析1.3，再从当前档案重建批次和目录；检查批次一致，并显式比较请求前安全回执保存的目录哈希与请求后新目录哈希。不能用模型省略的字段证明一致，也不能在比较前覆盖原哈希。
4. 校验器再重建目录并与可信批次目录完整比较，逐项验证编号在当前目录、主证据已选中、无重复引用及精确重复问题。未知、跨案、过期批次或篡改目录整批拒绝，不近似搜索、不补选标题、不删除条目。
5. 根据模型明确选择的编号逐字恢复主text和全部sources，直接复用旧证据绑定验证器；不经过1.2模型响应、不补造1.2字段。原始raw_output始终是原始1.3对象，不含程序注入的目录哈希。
6. 安全回执继续保存程序计算的pending_catalog_version/pending_catalog_sha256、选择编号/问题哈希、输出哈希及三层状态；pending_selection审计保存目录、目录SHA、原选择和恢复引用。格式/证据通过不改变semantic_status=pending_human_review。
7. 显式导入才写CaseStore。导入及ZIP恢复按1.3重建目录、核对回执SHA、选择与推断记录/证据锚点、完整输出审计。任意失败不写入现有案件，不重试。

PE编号对同一案件、同一来源的原文锚点是稳定的；其有效性由当前目录成员关系、批次上下文及程序的前后目录检查共同保证，不能仅凭编号曾在历史目录出现就信任它。目录SHA留在程序回执和审计中，并未取消完整性保护。

认证、明确批次授权、每份解析风险确认、QuotaStore共享调用与累计输入预算、冷却、并发、超时、零重试均复用原调用路径。请求仍一次完成四模块，不暗中增加调用。
